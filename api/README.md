# API — ระบบบริหารวิทยาลัยอาชีวศึกษาเอกชน

NestJS ครอบชั้นฐานข้อมูลใน [`../db`](../db) โดยไม่ย้ายกฎทางธุรกิจขึ้นมาไว้ในโค้ด

**สถานะ** — ทดสอบ end-to-end กับฐานข้อมูลจริงผ่านครบ 131 ข้อ (ระบบงาน 84 · ยืนยันตัวตน 30 · จำกัดคำขอ 6 · มาตรการระบบจริง 11) บน Node 26 และ PostgreSQL 18.4

19 โมดูล · 166 endpoint — สมุดคะแนน อนุมัติเกรด หลักสูตร ทวิภาคี สิทธิบุคลากร บันทึกการเข้าถึง การนำเข้าข้อมูล เอกสารของงานทะเบียน รอบสอบซ่อม และการเลื่อนชั้นปี ครบแล้ว

---

## เริ่มใช้งาน

```bash
cd api
npm install
cp .env.example .env      # แก้ DATABASE_URL และ JWT_SECRET
npm run build
npm start
```

API อยู่ที่ `http://localhost:3000/api/v1`

### เอกสาร OpenAPI

```bash
OPENAPI_ENABLED=true npm start   # แล้วเปิด http://localhost:3000/api/docs
```

**ปิดไว้เป็นค่าเริ่มต้นในระบบจริง** เพราะรายการ endpoint ทั้งหมดพร้อมบทบาท
ที่เรียกได้เป็นแผนที่ให้ผู้โจมตีอย่างดี เปิดชั่วคราวเมื่อต้องใช้แล้วปิดกลับ

เอกสารอ่านบทบาทจาก `@Roles()` และเพดานการยิงจาก `@Throttle()` ที่ guard
ใช้บังคับจริง ไม่ได้เขียนซ้ำอีกชุด — ถ้าเขียนซ้ำ ข้อมูลสองชุดจะค่อย ๆ
เพี้ยนจากกันแล้วเอกสารจะโกหกอย่างมั่นใจ ซึ่งแย่กว่าไม่มีเอกสาร

### รันเทสต์


## หลักการออกแบบ

### ฐานข้อมูลเป็นเจ้าของกฎ ชั้น API เป็นทางผ่าน

กฎทางธุรกิจอยู่ในฐานข้อมูลทั้งหมด — ตรวจเงื่อนไขลงทะเบียน คำนวณเวลาเรียน
ออกใบแจ้งหนี้ ตัดยอด กระทบยอด คำนวณความเสี่ยง ชั้น API แค่เรียกใช้และแปลงรูปแบบ

เหตุผล: กฎที่อยู่ในฐานข้อมูลบังคับใช้กับ **ทุกทาง** ที่เข้าถึงข้อมูล ไม่ว่าจะผ่าน API
ผ่าน pgAdmin ผ่านสคริปต์ย้ายข้อมูล หรือผ่านระบบอื่นที่ต่อเข้ามาในอนาคต
ถ้ายกกฎขึ้นมาไว้ในโค้ด ทางอื่นทั้งหมดจะข้ามกฎได้หมด

ผลที่ตามมาคือ service ส่วนใหญ่สั้นมาก และข้อความผิดพลาดภาษาไทยจากฐานข้อมูล
ไหลถึงผู้ใช้โดยตรง

### บริบทผู้ใช้ผ่าน AsyncLocalStorage และ SET LOCAL

`DbService` เป็นทางเดียวที่โค้ดแตะฐานข้อมูลได้ ทุกครั้งจะเปิด transaction แล้วตั้ง

```sql
select set_config('app.institution_id', $1, true),
       set_config('app.actor_id',       $2, true),
       set_config('app.role',           $3, true)
```

พารามิเตอร์ตัวที่สามคือ `is_local` เทียบเท่า `SET LOCAL` คือมีผลเฉพาะใน transaction นี้
**ต้องเป็น SET LOCAL ไม่ใช่ SET** เพราะถ้าค่าติดอยู่กับ connection ผู้ใช้คนถัดไป
ที่หยิบ connection เดิมจาก pool จะได้สิทธิ์ของคนก่อนหน้า ซึ่งเป็นช่องโหว่จริง
ที่เกิดบ่อยในระบบที่ใช้ connection pool ร่วมกับ RLS

ถ้าไม่มีบริบท `DbService.tx()` จะโยนข้อผิดพลาดทันที ไม่ยอมให้ query หลุดออกไปแบบไร้บริบท
งานเบื้องหลังต้องใช้ `runAs()` และระบุสถานศึกษาอย่างชัดเจน ไม่มีค่าเริ่มต้นให้เผลอใช้

### ปฏิเสธการเริ่มทำงานถ้าเชื่อมต่อด้วย superuser

ตอนบูต `DbService` ตรวจ `rolsuper` และ `rolbypassrls` ของผู้ใช้ที่เชื่อมต่อ
ถ้าข้าม RLS ได้จะโยนข้อผิดพลาดและแอปไม่ขึ้น

เหตุผล: superuser ข้าม Row-Level Security ทุกกรณี แปลว่ากำแพงกันข้อมูลข้ามวิทยาลัย
และกำแพงกันครูดูข้อมูลนักศึกษาที่ไม่ได้สอนจะไม่ทำงานเลย และ**ไม่มีอะไรฟ้อง**
ระบบจะดูเหมือนทำงานปกติจนกว่าจะมีคนร้องเรียน การล้มตั้งแต่บูตจึงดีกว่ามาก

### แปลงข้อผิดพลาดจากฐานข้อมูลเป็น HTTP ที่ถูกต้อง

| รหัส PostgreSQL | HTTP | ความหมาย |
|---|---|---|
| `P0001` raise exception | 422 | กฎทางธุรกิจไม่ผ่าน — ส่งข้อความไทยจากฐานข้อมูลต่อให้ผู้ใช้ |
| `23514` check violation | 422 | ลงทะเบียนไม่ได้เพราะติดเงื่อนไข |
| `23505` unique | 409 | ข้อมูลซ้ำ |
| `23P01` exclusion | 409 | ทับซ้อนกับรายการที่มีอยู่ |
| `23503` foreign key | 400 | อ้างถึงข้อมูลที่ไม่มีจริง |
| `42501` privilege | 403 | ไม่มีสิทธิ์ |

## ขั้นตอนอนุมัติเกรด

ครูผู้สอน → หัวหน้าแผนกวิชา → ฝ่ายวิชาการ → ผู้อำนวยการ → ล็อก

| ขั้น | บทบาทที่กดได้ |
|---|---|
| `teacher_submitted` | teacher · academic · admin |
| `head_approved` | teacher · academic · director · admin |
| `academic_approved` | academic · director · admin |
| `director_approved` | director · admin |
| `locked` | registrar · director · admin |
| `returned` (ตีกลับให้ครูแก้) | teacher · academic · director · registrar · admin |

**สองชั้นที่แยกหน้าที่กันชัดเจน** — ฐานข้อมูลบังคับ *ลำดับ* ของขั้น
ส่วนชั้น API บังคับ *ตัวบุคคล* ของแต่ละขั้น ต้องมีทั้งคู่ ถ้ามีแต่ลำดับ
ครูคนเดียวก็กดผ่านทั้งสายได้เอง ซึ่งทำให้ขั้นตอนอนุมัติไม่มีความหมาย

### แก้เกรดหลังล็อก

ล็อกแล้วแก้ไม่ได้ ต้องยื่นคำร้องที่บังคับผู้อนุมัติสองคน **และผู้ยื่นอนุมัติเองไม่ได้**

ความผิดพลาดเกิดขึ้นจริงเสมอ — กรอกคะแนนสลับคน ใบรับรองแพทย์ย้อนหลัง
หรือ ม.ส. ที่แก้เสร็จแล้ว ถ้าไม่มีทางแก้ที่ตรวจสอบได้ คนจะไปแก้ที่ฐานข้อมูล
ตรง ๆ แทน ซึ่งแย่กว่ามากเพราะไม่เหลือร่องรอยว่าใครแก้และเพราะอะไร

**สามชั้นที่กันคนละเรื่องกัน**

| ชั้น | กันอะไร |
|---|---|
| constraint ในตาราง | ผู้อนุมัติสองคนต้องเป็นคนละคน |
| trigger `grade_change_request_dual_control` | ตั้งผู้อนุมัติสองคนพร้อมกันในคำสั่งเดียวไม่ได้ · ผู้ยื่นอนุมัติเองไม่ได้ · สลับสาระคำร้องหลังมีคนอนุมัติแล้วไม่ได้ · ลบคำร้องไม่ได้ |
| ชั้น API | ครูกดอนุมัติไม่ได้เลย แม้ไม่ใช่ผู้ยื่น — ต้องผ่านสายบริหาร ไม่ใช่จบในห้องพักครู |

ใช้ trigger ไม่ใช่ `security definer` + RLS เพราะ `security definer` ทำให้ฟังก์ชัน
รันด้วยสิทธิ์เจ้าของซึ่งข้าม RLS ทั้งหมด แปลว่าครูของวิทยาลัยหนึ่งส่ง id
ของอีกวิทยาลัยเข้ามาก็ทำงานได้ — เป็นการแลกช่องโหว่ใหญ่กับการปิดช่องโหว่เล็ก
ส่วน trigger บังคับได้ทุกเส้นทางโดยไม่ต้องยกสิทธิ์ให้ใคร

คนที่สองกดอนุมัติแล้ว **ระบบแก้ให้ทันทีในธุรกรรมเดียว** ไม่แยกขั้น "อนุมัติแล้ว"
กับ "ลงมือแก้" เพราะจะเกิดสถานะค้างที่อนุมัติครบแล้วแต่เกรดยังเป็นค่าเดิม
ทั้งที่ทุกคนเข้าใจว่าแก้ไปแล้ว

`attendance_pct` ยกมาจากแถวเดิมโดยไม่คำนวณใหม่ เพราะเป็นค่าที่ตรึงไว้ ณ เวลาตัดเกรด

### ลำดับการตัดเกรด

`compute_section_grades()` ตัดสินตามลำดับนี้เสมอ

1. **เวลาเรียนไม่ถึงเกณฑ์ → ข.ร.** ไม่ต้องดูคะแนนเลย ต่อให้ได้คะแนนเต็ม
2. **กรอกคะแนนไม่ครบน้ำหนัก → ม.ส.** ไม่ใช่คิดจากคะแนนเท่าที่มี
3. นอกนั้นเทียบคะแนนถ่วงน้ำหนักกับ `grade_cutoff`

ข้อ 1 มาก่อนข้อ 3 เพราะระเบียบกำหนดว่านักศึกษาที่เวลาเรียนไม่ถึง
ไม่มีสิทธิ์เข้ารับการประเมินสรุปผล ระบบเก่ามักตัดจากคะแนนก่อนแล้วไล่แก้ ข.ร.
ทีหลังด้วยมือ ซึ่งตกหล่นเสมอ

`submit_section_grades()` ปฏิเสธถ้ากลุ่มยังมีคาบที่ยังไม่ได้สอน เพราะ
`pct_final` ระหว่างภาคต่ำโดยธรรมชาติ ถ้าปล่อยให้ส่งจะได้ ข.ร. ทั้งห้อง
โดยที่หน้าจอไม่มีอะไรผิดปกติให้เห็น

| `finance-holds` | `refresh_finance_holds()` — ระงับสิทธิ์คนค้างชำระ ปลดให้เองเมื่อชำระครบ |
| `purge-login-attempts` | ล้างบันทึกที่เกิน 90 วัน |

รันเองในโปรเซสตอน `JOBS_DAILY_AT` (ค่าเริ่มต้น 01:30 ตามนาฬิกาของโปรเซส)

**เมื่อรันหลาย instance ต้องตั้ง `JOBS_ENABLED=false`** แล้วให้ตัวตั้งเวลา
ของแพลตฟอร์มยิง `POST /jobs/run` เข้ามาแทน มิฉะนั้นทุก instance
จะรันงานเดียวกันพร้อมกัน

**วนทีละสถานศึกษาและดักข้อผิดพลาดแยกกัน** — `refresh_finance_holds()`
จะ raise ถ้าสถานศึกษานั้นยังไม่ได้ตั้งนโยบาย ถ้าปล่อยให้หลุดออกไป
สถานศึกษาแรกที่ตั้งค่าไม่ครบจะทำให้ที่เหลือทั้งหมดไม่ถูกประมวลผล
ซึ่งเป็นความล้มเหลวแบบเงียบที่แย่ที่สุด

## ทวิภาคีและการฝึกประสบการณ์

**ชั่วโมงที่ยังไม่รับรองไม่ใช่ชั่วโมงที่หายไป** — ทุก endpoint แยกสองตัวเสมอ
ตัวที่รับรองแล้วใช้ตรวจจบ ตัวที่รอรับรองแสดงในแอปให้นักศึกษาเห็นว่า
ที่ส่งไปแล้วยังรอครูนิเทศอยู่เท่าไร ระบบที่แสดงตัวเดียวทำให้นักศึกษา
คิดว่าที่บันทึกไปหายไปเฉย ๆ

**สถานประกอบการต้องผ่านประเมินก่อนจึงรับนักศึกษาได้** ตามระเบียบทวิภาคี
`POST /dual/placements` ปฏิเสธถ้าสถานะยังไม่เป็น `approved`

**นักศึกษาบันทึกชั่วโมงเองได้ แต่รับรองเองไม่ได้** — `verify_practicum_hours()`
ตรวจว่าผู้รับรองเป็นบุคลากรของวิทยาลัยจริง ไม่ใช่แค่จำกัดบทบาทที่ชั้น API

**ก่อน migration 0019 `practicum_log.workplace_id` ไม่มีตารางให้อ้างถึง**
ใส่ uuid อะไรก็ได้ ระบบไม่มีทางรู้ว่านักศึกษาฝึกที่ไหน ทั้งที่กฎจบข้อหนึ่ง
คือฝึกให้ครบ 320 ชั่วโมง

## สิทธิของบุคลากร

**ก่อน migration 0022 บทบาท registrar, finance, academic, director และ admin
ไม่มีทางผูกกับคนจริงได้เลย** — `roleOf()` คืนได้แค่ `teacher` กับ `student`
ทุกคนที่เป็นบุคลากรจะได้ `teacher` ไม่ว่าทำงานอะไร ผลคือในระบบจริงที่ปิด
`DEV_AUTH` งานทะเบียนออกใบแจ้งหนี้ไม่ได้ ฝ่ายวิชาการอนุมัติเกรดไม่ได้
และนโยบาย RLS ที่เขียนไว้อย่างละเอียดสำหรับบทบาทเหล่านั้นไม่เคยถูกใช้จริง

ตอนนี้บทบาทมาจากตาราง `staff_role` ที่มีช่วงเวลากำกับ ตอบได้ว่า
**ณ วันใดวันหนึ่งใครมีสิทธิ์อะไร** ซึ่งเป็นคำถามแรกที่ผู้ตรวจสอบถาม
เมื่อต้องยืนยันว่าการอนุมัติในอดีตชอบด้วยสิทธิ์

| ลำดับความแรง | บทบาท |
|---|---|
| 1 | `admin` |
| 2 | `director` |
| 3 | `registrar` |
| 4 | `academic` |
| 5 | `finance` |
| 6 | `student_affairs` |

ถือหลายบทบาทได้ตัวที่แรงที่สุด เพราะ token มีช่องบทบาทช่องเดียวและ RLS อ่านค่าเดียว

**มอบหมายและถอนสิทธิ์เป็นของ admin กับ director เท่านั้น** — ถ้าบทบาทอื่น
เขียน `staff_role` ได้ จะยกระดับตัวเองเป็น admin ในคำสั่งเดียว
ฐานข้อมูลบังคับซ้ำด้วยนโยบาย `staff_role_write`

**ตัดสิทธิ์มีสองแบบ** — `effective_to` คือวันสิ้นสุดวาระที่วางแผนไว้
ส่วน `revoked_at` คือตัดทันที ใช้ตอนพบการใช้สิทธิ์ในทางมิชอบหรือถูกให้ออกจากงาน
ถ้ามีแต่แบบแรกจะตัดสิทธิ์คนที่เพิ่งได้รับมอบหมายวันนี้ไม่ได้เลย

## บันทึกการเข้าถึงและเปลี่ยนแปลงข้อมูล

`grade_ledger` บันทึกเฉพาะการ **เขียน** ผลการเรียน แต่การรั่วไหลของข้อมูล
ส่วนบุคคลส่วนใหญ่คือการ **อ่าน** แล้วคัดลอกออกไป ซึ่งไม่ทิ้งร่องรอยเลย

| บันทึกอะไร | เมื่อไร |
|---|---|
| ทุกคำขอที่เปลี่ยนแปลงข้อมูล | อัตโนมัติ |
| การอ่านที่ติด `@Audit()` | เฉพาะที่ทำเครื่องหมายไว้ |
| คำขอที่ถูกปฏิเสธ | ด้วย — ความพยายามเข้าถึงที่ไม่มีสิทธิ์คือสิ่งที่ผู้ตรวจสอบสนใจที่สุด |

ไม่บันทึกทุก GET เพราะตารางจะโตเร็วกว่าข้อมูลจริงหลายเท่าจนหาอะไรไม่เจอ

**เจ้าของข้อมูลดูได้ว่าใครเข้าถึงข้อมูลตน** ที่ `GET /audit/me` ตาม PDPA มาตรา 30
และ **แก้หรือลบบันทึกไม่ได้แม้แต่ admin** — ลบได้เฉพาะแถวที่เกิน 90 วันแล้ว
ผ่าน `purge_access_log()` เพราะบันทึกการตรวจสอบที่แก้ได้ไม่มีค่าในการตรวจสอบ

## นำเข้าข้อมูลจากระบบเดิม

วิทยาลัยที่ย้ายมาใช้ระบบนี้มีนักศึกษาอยู่แล้วหลักพันคนพร้อมผลการเรียนย้อนหลัง
จะเริ่มจากฐานข้อมูลเปล่าไม่ได้

**สองขั้นเสมอ** — ขั้นที่ 1 ตรวจทุกแถวและคืนปัญหาทั้งหมดโดยไม่เขียนอะไร
ขั้นที่ 2 นำเข้าจริงเมื่อไม่เหลือปัญหา **มีแถวผิดแม้แถวเดียวจะไม่เขียนอะไรเลย**
เพราะข้อมูลที่เข้าไปครึ่งเดียวแก้ยากกว่าไม่เข้าเลย — ไม่มีใครรู้ว่าแถวไหนเข้าไปแล้ว

**คืนปัญหาทั้งหมดของแถว ไม่ใช่ข้อแรกที่เจอ** เหตุผลเดียวกับ `check_registration()`
ถ้าหยุดที่ข้อแรก เจ้าหน้าที่ต้องแก้แล้วนำเข้าใหม่หลายรอบ ซึ่งกับไฟล์พันแถว
คือการทำงานหลายวัน

**รับ JSON ไม่ใช่ CSV** เพราะการแปลง CSV ให้ถูกกับภาษาไทยมีกับดักเยอะ —
encoding (TIS-620 ที่ Excel ไทยยังใช้) ตัวคั่น การขึ้นบรรทัดในเซลล์ และ BOM
ให้ฝั่งหน้าจอที่รู้บริบทของไฟล์แปลงมาแล้วส่งเป็น JSON

**ประวัติการเรียนเก็บแยกจาก `enrollment_result`** ที่ `prior_academic_record`
เพราะผลที่นำเข้าไม่ได้ผ่านการตัดเกรดของระบบนี้ และไม่มีกลุ่มเรียนจริงรองรับ
การสร้างกลุ่มเรียนปลอมย้อนหลังจะทำให้รายงานภาระงานครูผิดทั้งหมด

หน่วยกิตที่ยังไม่อนุมัติเทียบโอนไม่ถูกนับ เหมือนชั่วโมงฝึกที่ยังไม่รับรอง —
การเทียบโอนเป็นดุลยพินิจของฝ่ายวิชาการ ไม่ใช่ผลอัตโนมัติของการนำเข้าไฟล์

## การยืนยันตัวตน

**แฮชรหัสผ่านด้วย scrypt ที่มากับ Node เอง** ไม่ใช้ bcrypt หรือ argon2 เพราะทั้งคู่
เป็น native module ที่ต้องคอมไพล์ตอนติดตั้ง ซึ่งพังบ่อยบน Windows และบน CI
ส่วน scrypt อยู่ในไลบรารีมาตรฐานอยู่แล้วและ OWASP รับรองให้ใช้กับรหัสผ่านได้
พารามิเตอร์ถูกเก็บไว้ในสตริงเดียวกับค่าแฮช จึงเพิ่มความแรงในอนาคตได้โดยไม่ต้อง
บังคับทุกคนตั้งรหัสใหม่ — ระบบจะแฮชใหม่ให้เองตอนเข้าสู่ระบบสำเร็จ

**ไม่เก็บ refresh token เก็บเฉพาะค่าแฮช** ถ้าฐานข้อมูลรั่วผู้โจมตีก็สวมสิทธิ์ไม่ได้
และหมุน token ใหม่ทุกครั้งที่ต่ออายุ ถ้าตรวจพบว่ามีการใช้ token ที่เพิกถอนแล้วซ้ำ
แปลว่าอาจถูกขโมย ระบบจะเพิกถอนทุก session ของคนนั้นทันที

**ผูกอุปกรณ์กับบัญชีนักศึกษา** เครื่องแรกอนุมัติเอง เครื่องถัดไปต้องให้งานทะเบียน
อนุมัติ เป็นมาตรการกันการยืมบัญชีกันเช็คอินแทน

**ผลข้างเคียงด้านความปลอดภัยต้อง commit ก่อนโยนข้อผิดพลาด** — ตัวนับครั้งที่ใส่ผิด
บันทึกความพยายามเข้าระบบ และอุปกรณ์ที่รออนุมัติ ถ้าเขียนไว้ใน transaction เดียวกับ
ที่โยนข้อผิดพลาด ฐานข้อมูลจะ rollback ทั้งหมด ผลคือใส่รหัสผิดกี่ครั้งบัญชีก็ไม่มีวัน
ถูกล็อก และเจ้าหน้าที่จะไม่เห็นอุปกรณ์ที่รออนุมัติเลย บั๊กนี้ถูกจับได้ตอนเขียนเทสต์

**เก็บไอพีเป็นค่าแฮช** ไอพีเป็นข้อมูลส่วนบุคคลตาม PDPA แต่ยังต้องใช้จำกัดจำนวนครั้ง
และตรวจสอบย้อนหลัง จึงแฮชพร้อมเกลือประจำระบบ (`IP_HASH_SECRET`)

**จำกัดจำนวนครั้งรายไอพีด้วย เพราะการล็อกบัญชีอย่างเดียวไม่พอ** — การล็อกบัญชี
กันการเดารหัสผ่านของ *บัญชีหนึ่ง* ได้ดี แต่กัน credential stuffing ไม่ได้เลย
ผู้โจมตีที่มีรายชื่อรหัสประจำตัวทั้งวิทยาลัย (เดาได้จากรูปแบบ `67201010xxx`)
ลองรหัสยอดนิยม **หนึ่งตัว** กับ **ทุกบัญชี** จะไม่ทำให้บัญชีไหนถูกล็อกสักบัญชี
เพราะแต่ละบัญชีถูกลองแค่ครั้งเดียว แต่มักได้บัญชีที่ตั้งรหัสง่ายไปอย่างน้อยหนึ่งบัญชี

ตัวนับรายไอพีอยู่ใน **ฐานข้อมูล** ผ่าน `login_rate_status()` ไม่ใช่หน่วยความจำ
ของโปรเซส เพราะตัวนับในหน่วยความจำจะถูกแบ่งตามจำนวน instance — รัน 3 instance
แปลว่าผู้โจมตีได้โควตาสามเท่าโดยอัตโนมัติ และรีสตาร์ททีเดียวโควตาก็คืนมาใหม่

ส่วน `ThrottleGuard` ที่นับในหน่วยความจำใช้กับ endpoint ทั่วไป ซึ่งเป้าหมายคือ
กันการยิงรัวจนเซิร์ฟเวอร์ล้ม ไม่ใช่การบังคับโควตาที่แม่นยำ จึงยอมรับข้อจำกัดนั้นได้
